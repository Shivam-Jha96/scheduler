Executive Summary

The In-WhatsApp Message Scheduler Chatbot enables any WhatsApp user (Alice) to message a bot conversationally inside WhatsApp to schedule text, media, or recurring reminders for future delivery to personal contacts or group chats (Bob).

1. The Sender Identity Paradox

Meta's official Cloud API dispatches messages from a corporate WABA phone number, not Alice's personal SIM—violating peer-to-peer expectations and triggering the strict 24-hour customer service window barrier (Error 131047).

2. Companion Anti-Ban & Session Security

Reverse-engineered WebSocket engines (@whiskeysockets/baileys) deliver authentic P2P messages from Alice's number, but require strict presence state machines, head-of-line per-JID pacing, and encrypted E2EE Signal key persistence.

3. Distributed Hybrid Scheduling

Combining durable PostgreSQL storage with a 60s Look-Ahead Feeder and a 5-minute BullMQ delayed buffer yields sub-second execution precision with <250 KB Redis RAM overhead and atomic cancellation semantics.

Engineering Scrutiny Report

V2.0 Architectural Audit: 10 Critical Gaps Identified & Rectified

10 / 10 Resolved in V2 Spec

A deep-dive technical audit of the V1 specification revealed 10 subtle but production-breaking bugs across the Baileys protocol layer, PostgreSQL state transitions, BullMQ race conditions, and cryptographic storage. All 10 have been rectified directly in this V2 Master Plan:

1. Baileys Deterministic Message ID Collision Protocol Bug

V1 Flaw: Passed a 64-char SHA-256 hex string directly as { messageId: idempotencyKey }. WhatsApp multi-device servers expect a compact uppercase stanza ID (typically 3EB0..., 16–22 hex chars) and silently drop or flag malformed 64-char IDs.

V2 Fix: Deterministically derive WA_MSG_ID = "3EB0" + SHA256(job_uid + ":" + next_run_iso).slice(0, 18).toUpperCase() (22 chars).

2. Sweeper Premature Re-Queue Race Condition Concurrency Bug

V1 Flaw: Look-Ahead Feeder stages jobs due in NOW() + 5m (`QUEUED`), while the Sweeper resets any `QUEUED` row where updated_at < NOW() - 5m. A job staged at T=4m59s is falsely flagged as orphaned right as BullMQ fires it!

V2 Fix: Sweeper predicates on next_run_at_utc < NOW() - INTERVAL '3 minutes' for `QUEUED` jobs, never updated_at.

3. User Edit / Cancel Race During 5-Min Buffer Data Integrity

V1 Flaw: If Alice runs /cancel or /edit when her job is already `QUEUED` inside BullMQ (T-4 mins), updating PostgreSQL alone fails to stop the in-flight Redis timer from firing stale data.

V2 Fix: Synchronous BullMQ queue.getJob(idempotencyKey)?.remove() on `/cancel` or `/edit` + mandatory worker DB state re-verification before socket write.

4. Baileys Pairing Code Flow (Single-Phone UX) UX Blocker

V1 Flaw: Relied solely on QR Code scanning to link Baileys. A user chatting with the bot on their smartphone cannot scan a QR code displayed inside a WhatsApp message on that same screen.

V2 Fix: Primary onboarding uses WhatsApp's 8-Character Alphanumeric Pairing Code (sock.requestPairingCode(phoneNumber)) sent directly in chat.

5. Per-User Head-of-Line Blocking in Anti-Ban Throughput Bug

V1 Flaw: If Alice schedules 5 messages at 9:00 AM, concurrent BullMQ workers simultaneously send overlapping composing frames from Alice's account, triggering instant Meta automated behavior flags.

V2 Fix: Per-Sender Redis Serialization Lock (pacing:user:) enforcing strictly sequential typing + 8–15s jitter per sender account.

6. Assistive Model 24h Self-Lockout Paradox Policy Bug

V1 Flaw: Section 3.1 claimed messaging Alice in the Assistive Reminder Model is always free-form compliant. If Alice schedules a message 3 days ahead and goes silent, Alice's own 24h window with the Bot expires!

V2 Fix: Pre-approved Meta Utility Template (scheduled_reminder_cta_v1) with dynamic CTA URL variable when now - alice_last_msg > 24h.

7. Envelope Encryption for E2EE Signal Keys Security Vulnerability

V1 Flaw: Stored raw Baileys creds JSONB and whatsapp_signal_keys BYTEA unencrypted in PostgreSQL. A database read compromise hijacks every user's personal WhatsApp identity.

V2 Fix: AES-256-GCM application-layer envelope encryption using KMS-backed Master Keys with per-row random 96-bit IV and authentication tags.

8. DST Spring-Forward & Fall-Back Ambiguity Temporal Edge Case

V1 Flaw: Did not define behavior when a recurring 2:30 AM job lands on a DST Spring-Forward gap (2:30 AM doesn't exist) or Fall-Back fold (2:30 AM occurs twice).

V2 Fix: Deterministic Luxon disambiguation: shift forward on non-existent spring-forward gaps; pin to first occurrence (offset: 'earlier') on fall-back folds.

9. Group Chat Membership & Admin Pre-Flight Delivery Failure

V1 Flaw: Allowed scheduling to @g.us group JIDs without verifying if Alice was removed from the group or if the group was switched to "Only Admins Can Send" (announce: true).

V2 Fix: Pre-flight groupMetadata(jid) check at T-60s staging; auto-transitions to FAILED (GROUP_RESTRICTED) and alerts Alice.

10. Media Payload Lifecycle & CDN Pre-Warming Storage & Latency

V1 Flaw: Stored media indefinitely in S3 and uploaded multi-megabyte videos to WhatsApp servers at the exact second of scheduled execution, causing 10–30s delivery lag.

V2 Fix: Pre-warm/encrypt media attachments during the T-5m Look-Ahead staging window + automated S3 Object Lifecycle TTL cleanup 24h after final execution.

8. Two-Tier Hybrid Scheduling Engine & Queue Synchronization

Why Pure Redis Fails

Holding 1M jobs scheduled months ahead in Redis ZSETs consumes ~1.8 GB of unpageable RAM and risks catastrophic loss on non-AOF restarts.

Why Pure DB Polling Fails

20 workers polling PostgreSQL every 1s generate 1.72M queries/day, causing index contention and noisy sub-second jitter.

Two-Tier Hybrid Winner

PostgreSQL holds long-term state (0 MB Redis RAM). A 60s Feeder stages only the next 5 minutes of jobs into BullMQ (<250 KB RAM).

Production Look-Ahead Feeder & Atomic Cancel/Edit Sync (TypeScript)

import { Queue } from 'bullmq';
import { Pool } from 'pg';
import crypto from 'crypto';

export function generateDeterministicIds(jobUid: string, nextRunUtcIso: string) {
  const sha256 = crypto.createHash('sha256').update(`${jobUid}_${nextRunUtcIso}`).digest('hex');
  // WhatsApp multi-device stanza IDs require '3EB0' prefix + 18 uppercase hex chars (22 chars total)
  const waClientMsgId = `3EB0${sha256.slice(0, 18).toUpperCase()}`;
  return { idempotencyKey: sha256, waClientMsgId };
}

export async function runLookAheadFeederTick(pgPool: Pool, bullQueue: Queue, workerId: string) {
  const client = await pgPool.connect();
  try {
    await client.query('BEGIN');

    // Claim up to 500 PENDING jobs maturing within the next 5 minutes
    const { rows } = await client.query(`
      SELECT id, job_uid, next_run_at_utc, idempotency_key, wa_client_msg_id
      FROM scheduled_jobs
      WHERE status = 'PENDING'
        AND next_run_at_utc <= (NOW() + INTERVAL '5 minutes')
      ORDER BY next_run_at_utc ASC
      LIMIT 500
      FOR UPDATE SKIP LOCKED
    `);

    if (rows.length === 0) {
      await client.query('COMMIT');
      return 0;
    }

    const nowMs = Date.now();
    const bulkJobs = rows.map((row) => {
      const targetMs = new Date(row.next_run_at_utc).getTime();
      const delayMs = Math.max(0, targetMs - nowMs);
      return {
        name: 'dispatch-whatsapp-job',
        data: {
          jobId: row.id,
          jobUid: row.job_uid,
          idempotencyKey: row.idempotency_key,
          waClientMsgId: row.wa_client_msg_id,
          expectedRunAtIso: new Date(row.next_run_at_utc).toISOString(),
        },
        opts: {
          jobId: row.idempotency_key, // Deduplicates inside Redis ZSET
          delay: delayMs,
          removeOnComplete: true,
          removeOnFail: 1000,
        },
      };
    });

    const ids = rows.map((r) => r.id);
    await client.query(`
      UPDATE scheduled_jobs
      SET status = 'QUEUED', locked_by = $1, locked_at = NOW(), updated_at = NOW()
      WHERE id = ANY($2::bigint[])
    `, [workerId, ids]);

    // Stage into BullMQ before committing DB transaction
    await bullQueue.addBulk(bulkJobs);
    await client.query('COMMIT');
    return rows.length;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

/**
 * Atomic User Cancellation: Prevents stale execution if job is already staged in BullMQ's 5-min window
 */
export async function cancelScheduledJob(pgPool: Pool, bullQueue: Queue, userId: string, jobUid: string) {
  const { rows } = await pgPool.query(`
    UPDATE scheduled_jobs
    SET status = 'CANCELLED', updated_at = NOW()
    WHERE job_uid = $1 AND user_id = $2 AND status IN ('PENDING', 'QUEUED', 'PAUSED')
    RETURNING idempotency_key
  `, [jobUid, userId]);

  if (rows.length > 0) {
    const stagedJob = await bullQueue.getJob(rows[0].idempotency_key);
    if (stagedJob) await stagedJob.remove();
    return true;
  }
  return false;
}

9. Recurrence Engine & DST-Safe Wall-Clock Calculation

Maintains Single Active Row Recurrence in scheduled_jobs. By converting UTC to the user's local IANA zone via Luxon, adding calendar intervals, and preserving the anchor day-of-month, a 9:00 AM reminder never drifts during seasonal DST transitions and never loses its 31st-of-the-month anchor after February. 

import { DateTime } from 'luxon';
import { parseExpression } from 'cron-parser';

export function computeNextLocalOccurrence(
  lastUtc: Date,
  anchorScheduledAtUtc: Date,
  userTz: string,
  type: string,
  recurrenceRule?: string | null
): { nextRunUtc: Date | null; isCompleted: boolean } {
  if (type === 'ONCE') return { nextRunUtc: null, isCompleted: true };

  if (type === 'CRON' && recurrenceRule) {
    try {
      const interval = parseExpression(recurrenceRule, { currentDate: lastUtc, tz: userTz });
      return { nextRunUtc: interval.next().toDate(), isCompleted: false };
    } catch {
      return { nextRunUtc: null, isCompleted: true };
    }
  }

  const local = DateTime.fromJSDate(lastUtc, { zone: userTz });
  const anchorLocal = DateTime.fromJSDate(anchorScheduledAtUtc, { zone: userTz });
  if (!local.isValid || !anchorLocal.isValid) return { nextRunUtc: null, isCompleted: true };

  let nextLocal: DateTime;

  switch (type) {
    case 'DAILY':
      nextLocal = local.plus({ days: 1 });
      break;
    case 'WEEKDAYS':
      nextLocal = local.weekday === 5 ? local.plus({ days: 3 })
                : local.weekday === 6 ? local.plus({ days: 2 })
                : local.plus({ days: 1 });
      break;
    case 'WEEKLY':
      nextLocal = local.plus({ weeks: 1 });
      break;
    case 'MONTHLY': {
      // Anchor Day Preservation: Jan 31 -> Feb 28 -> Mar 31 -> Apr 30 -> May 31
      const anchorDay = anchorLocal.day;
      const targetMonth = local.plus({ months: 1 });
      const maxDays = targetMonth.daysInMonth || 30;
      nextLocal = targetMonth.set({
        day: Math.min(anchorDay, maxDays),
        hour: anchorLocal.hour,
        minute: anchorLocal.minute,
        second: anchorLocal.second,
        millisecond: 0,
      });
      break;
    }
    default:
      throw new Error(`Unsupported recurrence type: ${type}`);
  }

  return { nextRunUtc: nextLocal.toUTC().toJSDate(), isCompleted: false };
}

/**
 * Reboot Fast-Forwarding: Steps overdue recurring jobs past nowUtc so server downtime
 * never triggers a burst of historical spam messages upon recovery.
 */
export function computeNextOccurrencePastNow(
  lastUtc: Date,
  anchorScheduledAtUtc: Date,
  userTz: string,
  type: string,
  recurrenceRule: string | null = null,
  nowUtc: Date = new Date()
): { nextRunUtc: Date | null; isCompleted: boolean } {
  let currentRun = lastUtc;
  let result = { nextRunUtc: null as Date | null, isCompleted: false };
  let iterations = 0;

  do {
    result = computeNextLocalOccurrence(currentRun, anchorScheduledAtUtc, userTz, type, recurrenceRule);
    if (result.isCompleted || !result.nextRunUtc) break;
    currentRun = result.nextRunUtc;
    iterations++;
  } while (result.nextRunUtc <= nowUtc && iterations < 1000);

  return result;
}

10. Zero-Double-Send Guarantee & Rectified Crash Recovery

Fixed Sweeper SQL Predicate

Every execution attempt is protected by a 4-Layer Deduplication Guard:

  1. BullMQ Job ID Uniqueness: Staged with opts: { jobId: idempotency_key } so overlapping Feeder ticks cannot enqueue duplicate timers.
  2. Redis Distributed Mutex & 24h Done Marker: Worker acquires SET lock:job: NX EX 60 and checks GET done:job: before touching the socket.
  3. PostgreSQL Pre-Flight State Verification: Worker executes UPDATE scheduled_jobs SET status='PROCESSING' WHERE id=$1 AND status='QUEUED' AND idempotency_key=$2. If Alice cancelled or edited the job during the 5-minute staging window, 0 rows match and the worker aborts cleanly.
  4. 22-Char Deterministic Stanza ID: Passed via sock.sendMessage(jid, payload, { messageId: waClientMsgId }) (e.g. 3EB09F8A2B1C4D5E6F7A8B). If a worker crashes mid-TCP ACK and retries, WhatsApp's server deduplicates the retry by stanza ID.

Rectified Dead-Man's-Switch Sweeper Query (Runs Every 2 Minutes)

-- V2.0 RECTIFIED SWEEPER:
-- 1. Recovers crashed PROCESSING workers whose lock_at is older than 5 minutes.
-- 2. Recovers orphaned QUEUED jobs ONLY when next_run_at_utc is >3 minutes in the past
--    (Prevents the V1 bug where jobs staged 5 minutes ahead were prematurely reset before firing!)
WITH stale_jobs AS (
    SELECT id, retry_count, max_retries, job_uid, status
    FROM scheduled_jobs
    WHERE (
        status = 'PROCESSING'
        AND locked_at < (NOW() - INTERVAL '5 minutes')
    ) OR (
        status = 'QUEUED'
        AND next_run_at_utc < (NOW() - INTERVAL '3 minutes')
    )
    FOR UPDATE SKIP LOCKED
)
UPDATE scheduled_jobs
SET status = CASE
        WHEN stale_jobs.status = 'PROCESSING' AND stale_jobs.retry_count + 1 >= stale_jobs.max_retries
        THEN 'FAILED'::job_status_enum
        ELSE 'PENDING'::job_status_enum
    END,
    retry_count = CASE
        WHEN stale_jobs.status = 'PROCESSING' THEN stale_jobs.retry_count + 1
        ELSE stale_jobs.retry_count
    END,
    locked_at = NULL,
    locked_by = NULL,
    last_error = CASE
        WHEN stale_jobs.status = 'QUEUED'
        THEN 'Recovered orphaned QUEUED job past scheduled execution window (Redis flush/stall)'
        ELSE 'Stale PROCESSING lock recovered: Worker heartbeat expired after 5 minutes'
    END,
    updated_at = NOW()
FROM stale_jobs
WHERE scheduled_jobs.id = stale_jobs.id;

Per-User Outbound Serialization & Presence Pacing

A human cannot type in two chats simultaneously. Before dispatching via Baileys, the worker acquires a per-sender Redis token lock pacing:sender::

  • Step 1: Send sock.sendPresenceUpdate('available', jid).
  • Step 2: Send sock.sendPresenceUpdate('composing', jid).
  • Step 3: Hold Gaussian typing delay: $T_{\text{type}} = \min(5.0, \text{len} \times 0.04 + \mathcal{N}(1.5, 0.4))\text{ s}$.
  • Step 4: Send sock.sendPresenceUpdate('paused', jid) & transmit message with waClientMsgId.
  • Step 5: Hold cooldown lock for 8–15s jitter before releasing pacing:sender:.

export function encryptSignalBlob(plainBuf: Buffer, masterKey: Buffer) {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv('aes-256-gcm', masterKey, iv);
  const encrypted = Buffer.concat([cipher.update(plainBuf), cipher.final()]);
  return { encrypted, iv, authTag: cipher.getAuthTag() };
}
