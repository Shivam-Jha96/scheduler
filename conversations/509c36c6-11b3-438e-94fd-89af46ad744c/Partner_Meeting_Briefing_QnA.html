Theme 1: Technical Architecture & Core Scheduling
Q1 What were the audit gaps identified between V1 and V2, and why do they matter?

In moving from the initial spike to an enterprise-grade production architecture, we conducted an exhaustive failure-mode audit and fixed 10 critical production edge cases:

1. Baileys 22-Char Stanza IDs: WhatsApp silently drops messages if the socket stanza ID is not strictly 22 alphanumeric characters. We enforce valid stanza generation.
2. Feeder vs. Sweeper Race: Separated polling time windows so the 60s feeder and the 5m crash recovery sweeper never grab or dispatch the same message twice.
3. In-Flight BullMQ Eviction: If Alice cancels a message loaded in Redis memory 2 minutes before send time, the system actively removes the job via job.remove().
4. Single-Phone Pairing Code: Scanning QR codes requires a second screen. We implemented WhatsApp's native 8-digit pairing code (1234-5678) for 1-tap mobile pairing.
5. Per-Sender Typing Locks: Parallel socket transmissions from one phone number trigger instant spam bans. We serialize sends with realistic 3–6s typing delays.
6. 24-Hour Meta Cloud API Fallback: Automatically falls back to an approved Utility Template with a deep-link button if the 24-hour customer window is closed.
7. Signal Pre-Key AES-256 Encryption: Session keys grant full cryptographic control over WhatsApp accounts. We mandate AES-256-GCM envelope encryption with AWS KMS.
8. DST Gap & Fold Handling: Handled Daylight Saving Time shifts via Luxon disambiguation so 9:00 AM local time never drifts or double-fires across seasonal clock shifts.
9. Group Membership Pre-Flight: Prevents socket crashes by verifying active group membership before executing scheduled group broadcasts.
10. S3 Media Pre-Warming: Large image/document attachments are pre-cached into server RAM 30 seconds prior to scheduled dispatch to ensure sub-second delivery.
Q7 How does the BullMQ Hybrid Approach work in simple terms?
Core Analogy: Think of the scheduling system as an airport operation:
  • Why not Database-Only (PostgreSQL)? If 100,000 users schedule messages and you poll PostgreSQL every second, database CPU spikes to 100% and crashes under disk I/O lock contention.
  • Why not Queue-Only (Redis/BullMQ)? Redis stores jobs in RAM. Storing 100,000 messages scheduled 6 months out in Redis is financially wasteful, and if Redis restarts, long-term scheduled data could be lost.
  • The Two-Tier Solution:
    1. PostgreSQL is the "Cold Warehouse": All 100,000 messages sit cheaply and durably on persistent disk.
    2. The 60-Second Feeder is the "Conveyor Belt": Every 60 seconds, a background process queries: "Give me messages due in the next 5 minutes."
    3. BullMQ (Redis) is the "Launchpad": Only messages due within the immediate 5 minutes are held in RAM. BullMQ counts down and fires them with millisecond precision.
Q10 What is the "Sliding Buffer" (5-Minute Delay)? Does it delay message delivery?

No, it does NOT delay message delivery. The message is delivered at the exact second scheduled.

"Sliding buffer" refers to our look-ahead staging window. If a message is scheduled for 10:00:00 AM, the Feeder transfers the job from PostgreSQL into Redis at 9:55:00 AM with a 5-minute countdown timer. At 10:00:00.050 AM, BullMQ hits zero and fires immediately. This 5-minute cushion absorbs server spikes and network jitters so no deadline is ever missed.

Q14 Elaboration on Section 12 (Hybrid Queue Engine) and Section 16 (Zero-Double-Send Guarantee)
Section 12 — Two-Tier Hybrid Scheduling Engine:

The Feeder executes SELECT ... FOR UPDATE SKIP LOCKED on PostgreSQL 16 to guarantee that multiple horizontal feeder instances never lock or process duplicate records. Jobs are pushed into BullMQ with deterministic IDs (jobId = scheduled_message.id), guaranteeing single-instance registration in Redis.

Section 16 — Zero-Double-Send Guarantee & Recovery Sweeper:

Enforces a 4-tier safety shield: (1) DB row lock on claim, (2) BullMQ unique job ID deduplication, (3) Atomic Redis lock SET lock:msg:{id} NX EX 600 right before socket transmission, and (4) An independent Recovery Sweeper running every 5 minutes that recovers stale jobs orphaned by sudden worker node crashes without overlapping with the live feeder.

Q15 What is the difference between Anchor Time and Scheduler Time?
  • Anchor Time: The user's intended local wall-clock time in their IANA timezone (e.g., 09:00:00 AM in America/New_York). This is permanent and invariant to seasonal shifts.
  • Scheduler Trigger Time: The absolute UTC timestamp calculated for physical server dispatch (e.g., 14:00:00 UTC during standard time, shifting to 13:00:00 UTC during daylight saving time).
  • When Updating: The user updates the Anchor Time; the recurrence engine re-computes the corresponding UTC Scheduler Time automatically.

If Meta introduces a basic "Send Later" feature (similar to Telegram or iOS 18), our business remains defensible through four distinct moats:

  1. Omnichannel Unified Hub: WhatsApp will never schedule to Viber, Signal, Discord, or Telegram. We become the single command center across all messaging ecosystems.
  2. Advanced Recurrence & Business Logic: Any native WhatsApp tool will only support simple one-off delays. It will not handle complex business rules: "Every 2nd Tuesday except bank holidays", "Follow up in 48 hours if no reply", dynamic CRM variable injection, or Google Sheets sync.
  3. Headless Cloud Persistence: Native mobile schedulers (like Signal or Android SMS) die if the phone battery runs out or loses network. Our cloud scheduler fires 100% reliably 24/7/365 regardless of device status.
  4. Team Collaboration & Shared Inboxes: Multi-seat scheduling, manager approvals, and team-wide audit logs for agencies.

Theme 4: Security, PII, Storage & Unit Economics
Q6 PII, Security Policies, and Database Hosting Cost Inclusion

1. PII & Privacy Architecture:

  • Envelope Encryption: Baileys session keys and authentication tokens are encrypted at the application layer with AES-256-GCM using AWS KMS master keys before database writes.
  • Ephemeral Retention Policy: Once a scheduled message is dispatched, message content is permanently scrubbed from the active database; only an anonymized delivery receipt and SHA-256 verification hash are kept for auditing.
  • Zero Contact Scraping: We never harvest or upload Alice's complete contact address book—only the specific recipient phone numbers she schedules messages for.

2. Infrastructure Hosting Costs (10,000 Active Users):

Managed PostgreSQL ($35/mo) + Redis BullMQ ($20/mo) + Node.js VPS cluster ($60/mo) = ~$115 / month total infrastructure. At ~$0.012 per active user/month, hosting charges are negligible and fully absorbed into subscription pricing.

Theme 5: User Experience, Delivery Modes & Recurrence
Q8 In the Cloud API Assistive Model (Section 3A), does Alice just click a button to send?

Yes, exactly. At the scheduled time, the bot sends Alice an interactive WhatsApp message: "⏰ Time to send your scheduled message to Bob!" with an actionable button: [ 🚀 Send Message to Bob ].

Tapping the button deep-links into Alice's native 1-on-1 WhatsApp chat with Bob with the text already pre-filled in the input box. Alice just taps Send. This provides a 100% Meta-compliant experience with zero risk of account ban for users who prefer not to link companion sessions.

Q9 Is Baileys Companion Pairing limited to 24 hours or permanent for months?

It is permanent for months. It does NOT expire in 24 hours.

The 24-hour window applies only to Meta's corporate Cloud API (customer service window). Baileys uses WhatsApp's native Multi-Device companion protocol (identical to WhatsApp Web / Desktop). WhatsApp only unlinks companion devices if Alice's primary phone stays completely offline for more than 14 consecutive days. If Alice uses her phone normally, the link persists indefinitely.

Q12 Weekly Recurrence: Can users edit an existing schedule, or must they cancel and recreate?

Both options are fully supported:

  • In-Place Editing: Users can send /edit <id> to change the send time, update the message text, or adjust recurrence rules (e.g., switching from Mondays to Tuesdays).
  • Cancellation: Users can send /cancel <id> to cancel upcoming iterations.
  • Under the Hood: We use a Single-Active-Row FSM. Exactly one row exists in the database for that schedule. When Monday's message is delivered, the system calculates next Monday's date and updates the same database row in place.

Theme 6: Anti-Abuse & Spam Prevention
Q16 How do we prevent spamming? Can Alice schedule a message to 100 users at the same time?

To protect user accounts from being flagged or banned by WhatsApp, the platform enforces four multi-layered safeguards:

  • Serialization & Inter-Message Jitter: If Alice schedules a message to 100 contacts for 9:00 AM, the scheduler never sends 100 messages at 9:00:00 AM. It serializes them sequentially, adding 3 to 6 seconds of randomized delay plus realistic typing indicator emulation between each recipient. The 100 messages are smoothly distributed across an 8- to 10-minute window.
  • Account Rate Limits: Personal companion sessions are hard-capped at 5 messages per minute and 50 messages per hour.
  • Tier-Based Quotas: Free users can only schedule for 1 to 5 contacts per batch. Large batch broadcasts are restricted to verified Business accounts.
  • Emergency Circuit Breakers: If WhatsApp returns an error 403 or triggers recipient spam feedback, the system immediately freezes all pending outbound jobs for that sender to safeguard their phone number from a permanent SIM ban.
